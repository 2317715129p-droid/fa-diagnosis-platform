## 一、部署前置检查

### 1.1 硬件最低要求

| 项目 | 最低要求 | 推荐配置 |
|------|---------|---------|
| CPU | 4 核 | 8 核以上 |
| 内存 | 8 GB | 16 GB 以上 |
| 系统盘 | 60 GB 可用 | 120 GB SSD |
| 系统 | Ubuntu 20.04/22.04/24.04 LTS | Ubuntu 22.04 LTS |
| 架构 | x86_64 | x86_64 |

> ⚠️ 内存不足 8 GB 时，部署脚本会自动创建 8 GB swap 文件。生产环境建议直接配到 16 GB。

### 1.2 网络要求

- **3000 端口（TCP）**：FA 前端 + API 转发，外网放行
- **80 端口（TCP）**：Dify 控制台，外网放行
- **11434 端口（TCP）**：Ollama 推理接口（仅内网通信，外网建议关闭）
- **8000 端口（TCP）**：FastAPI 后端直连（可选，3000 已代理转发）

被监控服务器 → 中心服务器：只需放行 **3000 端口** TCP 即可（Agent 从 3000 下载脚本、从 3000 推送数据）。

### 1.3 操作系统预检查

```bash
# 确认 Ubuntu 版本
cat /etc/os-release

# 确认磁盘空间
df -h / | tail -1

# 确认内存
free -h

# 确认未被占用以下端口（3000 / 80 / 8000 / 11434 / 5432 / 6379）
sudo ss -tlnp | grep -E ':(3000|80|8000|11434|5432|6379)\b'

# 若以上端口有占用且非必要，停止旧进程
# sudo systemctl stop nginx     # 如 80 被系统 nginx 占用
# sudo systemctl stop postgresql # 如 5432 被系统 postgres 占用
```

### 1.4 必须有 root 或 sudo 权限

所有部署命令均使用 `sudo`，普通用户需要在 sudoers 中。

## 二、离线包准备与上传

### 2.1 确认本地离线包文件

`d:\idex\offline\` 下以下 **6 个文件**全部必须齐全（无一可选，缺一不可）：

| # | 文件名 | 大小 | 作用 |
|---|--------|------|------|
| 1 | `install-all.sh` | < 10 KB | 一键部署入口脚本 |
| 2 | `fa-diagnosis-offline-clean.tar.gz` | 2.5 GB | 主程序离线包（FA + Dify + deploy-images.tar 镜像包） |
| 3 | `fa-export-bundle.tar.gz` | 85 MB | 服务器配置导出包（工作流、数据卷、私钥、模型配置） |
| 4 | `qwen2-7b.gguf` | 4.1 GB | Qwen2:7B 大语言模型文件 |
| 5 | `dify-plugin-daemon-0.6.3-local.tar` | 580 MB | Dify 插件守护进程镜像（主包 deploy-images.tar 不含此镜像，**必须单独上传**） |
| 6 | `weaviate-1.27.0.tar` | ~600 MB | Weaviate 1.27.0 镜像（主包 deploy-images.tar 只有 1.19.0，compose 要求 1.27.0，**必须单独上传**） |

> ⚠️ 第 6 个文件 `weaviate-1.27.0.tar` 需要从**旧服务器导出**（见 2.2 节）。

### 2.2 从旧服务器导出 weaviate:1.27.0 镜像（清空服务器前做！）

主包 `deploy-images.tar` 里只有 `weaviate:1.19.0`，但 `docker-compose.yml` 要求 `1.27.0`。必须从当前服务器导出：

```bash
# 在当前服务器上执行（清空之前！）
docker save semitechnologies/weaviate:1.27.0 -o /opt/weaviate-1.27.0.tar
ls -lh /opt/weaviate-1.27.0.tar
```

然后用 scp 下载到本地 `d:\idex\offline\`：

```powershell
# 本地 PowerShell 执行
scp root@<旧服务器IP>:/opt/weaviate-1.27.0.tar d:\idex\offline\
```

> ⚠️ 如果你已经清空了服务器且没有这个镜像，weaviate 服务将无法启动。需另找一台有 weaviate:1.27.0 镜像的机器导出，或改 docker-compose.yml 版本（有数据兼容风险，不推荐）。

### 2.3 上传到目标服务器

用 `scp`（或 WinSCP / FileZilla）将以上 **6 个文件**全部上传到新服务器的 `/opt` 目录下：

```powershell
# 在本地 PowerShell 执行（把 <SERVER_IP> 换成新服务器公网 IP）
scp d:\idex\offline\install-all.sh                    root@<SERVER_IP>:/opt/
scp d:\idex\offline\fa-diagnosis-offline-clean.tar.gz root@<SERVER_IP>:/opt/
scp d:\idex\offline\fa-export-bundle.tar.gz            root@<SERVER_IP>:/opt/
scp d:\idex\offline\qwen2-7b.gguf                      root@<SERVER_IP>:/opt/
scp d:\idex\offline\dify-plugin-daemon-0.6.3-local.tar root@<SERVER_IP>:/opt/
scp d:\idex\offline\weaviate-1.27.0.tar                root@<SERVER_IP>:/opt/
```

上传完成后，在服务器端确认：

```bash
ls -lh /opt/*.sh /opt/*.tar.gz /opt/*.gguf /opt/*.tar 2>/dev/null
```

期望输出类似（**6 个文件全部可见**）：

```
-rw-r--r-- 1 root root 2.5K Aug 13 12:00 /opt/install-all.sh
-rw-r--r-- 1 root root 2.5G Aug 13 12:00 /opt/fa-diagnosis-offline-clean.tar.gz
-rw-r--r-- 1 root root  85M Aug 13 12:00 /opt/fa-export-bundle.tar.gz
-rw-r--r-- 1 root root 4.1G Aug 13 12:00 /opt/qwen2-7b.gguf
-rw-r--r-- 1 root root 580M Aug 13 12:00 /opt/dify-plugin-daemon-0.6.3-local.tar
-rw-r--r-- 1 root root 600M Aug 13 12:00 /opt/weaviate-1.27.0.tar
```

## 三、一键部署（8 步全自动）

### 3.1 进入 /opt 目录，执行部署

```bash
cd /opt
sudo chmod +x install-all.sh

# 把 <新服务器公网IP> 换成你这台服务器的公网 IP，例如 47.99.140.203
sudo bash install-all.sh <新服务器公网IP>
```

全程耗时约 **15-40 分钟**（取决于硬件速度）。脚本会依次执行以下 8 步：

1. **[1/8]** 解压离线主包 → `/opt/fa`
2. **[2/8]** 安装基础环境（Docker / 加载 Docker 镜像）
3. **[3/8]** 检查并加载 dify-plugin-daemon 镜像
4. **[4/8]** 创建必要的 Docker Volume
5. **[5/8]** 检查内存，不足自动创建 8 GB swap
6. **[6/8]** 解压服务器配置导出包 `fa-export-bundle.tar.gz`
7. **[7/8]** 复制 qwen2 模型到安装目录
8. **[8/8]** 恢复配置、数据卷、Ollama 模型、Dify 工作流、插件超时修改

### 3.2 部署成功标志

脚本最后输出如下表示成功：

```
==============================================
  FA 系统部署完成
==============================================

  前端(3000): 200
  后端(8000): 200
  Dify(80):   200
  Ollama:     200
```

四个服务全部返回 `200` 为正常。

> ⚠️ 如果哪一步报错，不要重试。先翻到**第七章 FAQ** 按对应错误条目排查，解决后再跑。

## 五、Agent 自动采集部署

### 5.1 在被监控服务器上一键安装 Agent

在**被监控硬件服务器**（非中心服务器）root 用户下执行：

```bash
# 把 <中心服务器IP> 换成 FA 中心服务器的公网 IP
curl -fsSL "http://<中心服务器IP>:3000/api/agent/install.sh?server_id=Node-01" | sudo bash
```

> 注意：
> - URL 两边用**双引号**，**不要加反引号**（加反引号会导致 shell 命令替换）
> - `server_id=` 可以自定义，例如 `server_id=DB-Server-01`、`server_id=Compute-Node-07`
> - 被监控服务器需要有 `curl/wget`、`python3`、`ipmitool`（脚本会自动安装这些依赖）

安装成功输出：

```
==============================================
  FA Diagnosis Agent installed
==============================================
  SERVER_ID : Node-01
  CENTER    : http://<中心服务器IP>:3000/api/collect
  Logs      : /var/log/fa-agent/collector.log
==============================================
```

### 5.2 验证数据上报到中心

#### 被监控服务器侧

```bash
# 立即触发一次采集（timer 是 5 分钟一次）
sudo systemctl start fa-collector.service && sleep 5

# 看采集日志（应该有 push ok 字样）
journalctl -u fa-collector.service -n 15 --no-pager
tail -20 /var/log/fa-agent/collector.log
```

正常日志应包含：

```
[info] no new hardware logs; sending heartbeat only
[info] push ok status=200 lines=0
[info] FA agent done
```

#### 中心服务器侧（FA 前端验证）

打开 `http://<中心服务器IP>:3000` → **自动采集** 页：

- 资产列表中应该出现对应 `server_id` 的机器
- 状态：**在线**（10 分钟内有心跳 = 在线，30 分钟 = 过期，超时 = 离线）
- 点击机器可查看历史日志和诊断结果

## 六、服务健康检查与日常操作

### 6.1 健康检查

服务器上一条命令检查所有组件：

```bash
echo "=== Docker 容器状态 ==="
docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}" | grep "^fa-"

echo "
=== HTTP 检查 ==="
IP=$(hostname -I | awk '{print $1}')
curl -s -o /dev/null -w "FA前端(3000):    %{http_code}\n" http://localhost:3000
curl -s -o /dev/null -w "FA后端(8000):    %{http_code}\n" http://localhost:8000/health
curl -s -o /dev/null -w "Dify控制台(80):   %{http_code}\n" http://localhost
curl -s -o /dev/null -w "Ollama(11434):    %{http_code}\n" http://localhost:11434

echo "
=== Ollama 模型 ==="
docker exec fa-ollama ollama list 2>/dev/null || echo "  [WARN] 未加载模型"

echo "
=== Agent 资产数（最近 24h 活跃） ==="
docker exec -i fa-postgres psql -U postgres -d dify -t \
  -c "SELECT count(*) FROM assets WHERE last_seen_at > NOW() - INTERVAL '24 hours';" 2>/dev/null \
  || echo "  [INFO] 若无资产，或 FA 使用 SQLite，跳到下一条"
```

### 6.2 常用运维命令

```bash
cd /opt/fa

# 停止所有服务（保留容器状态，下次启动快）
docker compose -p fa stop

# 停止并删除容器（保留 volume 数据）
docker compose -p fa down

# 启动所有服务
docker compose -p fa up -d

# 查看单个服务日志
docker logs -f fa-frontend     # 前端 + Nginx
docker logs -f fa-backend      # 后端（FastAPI）
docker logs -f fa-ollama       # Ollama 推理（知识库切片时看这里）
docker logs -f fa-plugin-daemon # Dify 插件（推理超时看这里）
docker logs -f fa-postgres     # Postgres
docker logs -f fa-dify-api     # Dify API

# 重启服务组
docker compose -p fa restart backend frontend
docker compose -p fa restart ollama plugin-daemon

# 查看磁盘占用大户
docker system df
du -sh /var/lib/docker/volumes/fa_*
```

## 七、常见问题速查（FAQ）

### ❌ Q1：install-all.sh 报错 "Bundle not found: fa-diagnosis-offline-clean.tar.gz"

**原因**：主包没上传到 /opt，或文件名不对。
**解决**：
```bash
ls -lh /opt/*.tar.gz /opt/*.tar
# 确认 fa-diagnosis-offline-clean.tar.gz 在 /opt 下
# 如果只有 fa-diagnosis-offline.tar.gz，也可以（脚本已兼容两种文件名）
```

### ❌ Q2："Installation directory exists: /opt/fa. Use --force to overwrite."

**原因**：重新部署时旧目录还在。
**解决**：脚本已内置 `--force`，通常不会出；若出现，手动执行：
```bash
# 不删 volume 数据，仅清安装目录
cd /opt/fa && docker compose -p fa down 2>/dev/null; cd /opt && rm -rf /opt/fa
# 重新跑 install-all.sh
```

### ❌ Q3：Agent 安装失败 "failed to download collector.py (check center URL / firewall)"

**原因 1（旧版）**：历史上 nginx Host 丢端口导致 URL 变成 80 端口。**本版已修复**，不应再出现。

**排查（新版）**：
```bash
# 1. 从被监控服务器直连中心 3000，测能否下载
curl -v "http://<中心IP>:3000/api/agent/collector.py" | head -5
# 应返回 Python 代码（带 FA hardware monitoring agent 字样），不是 404

# 2. 看 center URL 是否正确（应带 :3000）
curl -s "http://<中心IP>:3000/api/agent/install.sh?server_id=Node-01" | grep -E "CENTER_URL|COLLECTOR_URL"
# 应输出：CENTER_URL='http://<中心IP>:3000/api/collect'
#        COLLECTOR_URL='http://<中心IP>:3000/api/agent/collector.py'
```

如果 center URL **不带 :3000**，说明前端镜像没 rebuild（用了旧 nginx.conf）。执行：

```bash
cd /opt/fa && docker compose -p fa build --no-cache frontend && docker compose -p fa up -d frontend
```

### ❌ Q4：Agent 安装成功但 FA 前端看不到资产（在线不显示）

**原因**：被监控机器是虚拟机（阿里云/腾讯云 ECS），没有真实 IPMI，collector 采集到空数据后**早期版本会提前退出不上报**。**本版已修复**（空数据也会发心跳）。

**排查**：
```bash
# 被监控服务器上：检查 collector.py 是否包含心跳关键字
grep "sending heartbeat" /opt/fa-agent/collector.py
# 若无 → 说明旧版没替换，手动 patch：
python3 -c "
p='/opt/fa-agent/collector.py';t=open(p).read()
old='nothing new to push; exit\")\n        return 0'
new='no new hardware logs; sending heartbeat only\")'
if old in t: open(p,'w').write(t.replace(old,new));print('patched')
else: print('no need')
"

# 立即触发一次上报
sudo systemctl start fa-collector.service && sleep 5
journalctl -u fa-collector.service -n 10 --no-pager | grep "push ok"
```

### ❌ Q5：Dify 调用模型时报错 "[models] Connection Error" / PluginTimeout

**原因**：Ollama 容器与 Dify 通信问题，或模型推理太慢（qwen2:7b CPU 推理 5-10 tok/s），被 PluginDaemon 300s 超时杀死。

**排查**：
```bash
# 1. 直连测 Ollama 是否正常
docker exec fa-ollama ollama run qwen2:7b "你好" --verbose

# 2. 看 plugin-daemon 日志
docker logs -f fa-plugin-daemon --tail 50
# 如果有 timeout=300，脚本的 sed 修改未生效，手动再跑一次：
docker exec fa-plugin-daemon find /app/storage/langgenius -name "*.py" -exec sed -i 's/timeout=(10, 300)/timeout=(10, 2000)/g' {} \;
docker restart fa-plugin-daemon && sleep 10
```

### ❌ Q6：知识库切片失败，Weaviate 报 503 / cluster join 失败

**排查**：
```bash
docker exec fa-weaviate curl -s http://localhost:8080/v1/.well-known/ready
# 必须返回 200 OK

# 如果不是 200，重启 weaviate
docker restart fa-weaviate && sleep 10
```

### ❌ Q7：前端 API 返回 404（Nginx 转发失败）

**排查**：
```bash
# 先测后端直连是否正常
curl -v http://localhost:8000/health
# 正常应返回 {"status":"ok"}

# 再测 Nginx 代理（如果直连 OK 但代理不通 → Nginx 配置错）
curl -v http://localhost:3000/api/assets | head -5
```

### ❌ Q8：磁盘空间不足，Docker build 报错 "no space left on device"

```bash
# 清理 Docker 无用缓存
docker system prune -af --volumes

# 查大文件占用
du -sh /var/lib/docker/*
du -sh /opt/fa/* | sort -hr | head -10
```

## 八、已修复的坑（历史问题清单）

> 本离线包 v2.0 对比 v1.0 修复了以下所有已知问题。**部署时不需要再手动热改任何配置。**

| # | 修复点 | 影响 |
|---|--------|------|
| 1 | 新增 `frontend` 服务定义到 docker-compose.yml，映射 `3000:3000` | ✅ FA 前端可独立访问，不再被 Dify 3000 抢占 |
| 2 | backend 和 frontend 同时加入 `fa_network` 和 `default` 网络 | ✅ 解决后端无法解析 dify-* 服务名的网络隔离问题 |
