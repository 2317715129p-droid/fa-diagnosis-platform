# FA 报告写作规范

**文档定位**：本规范是 AI 生成硬件故障诊断报告时必须遵守的格式约束和内容规范，作为 RAG 知识库的核心参考文档。

**适用范围**：Dify 工作流 LLM 推理节点的 System Prompt 补充依据；FastAPI 后处理校验的格式基线。

**版本**：v1.0

**来源**：项目设计书 §4.5 RAG 知识库检索、§4.6 AI 诊断推理、§4.7 后处理兜底机制

## 1. 报告模板概述

FA 诊断报告必须严格遵循**四段式 Markdown 结构**，每段有明确的必填字段和格式要求：

| 段落 | 核心内容 | 必填字段 |
|---|---|---|
| 第一段 | 故障现象定位 | 故障部件、物理位置、报错代码、故障等级 |
| 第二段 | 物理根因推导 | 失效物理成因分析 + 知识库依据标注 |
| 第三段 | 工程处置建议 | 紧急处置、根治方案、验证方法 |
| 第四段 | 置信度评估 | 诊断置信度（高/中/低）+ 说明 |

**输出语言**：中文，技术术语保留英文原文（如 Electromigration、Row Hammer、Internal Parity Error 等）。

**格式要求**：严格使用 Markdown 三级标题 ### 分隔四段，严禁删减任何章节，严禁添加额外章节。

## 2. 四段式报告模板

以下为完整模板，方括号 [] 内为需根据实际故障填充的内容：

```markdown

从微电子与硬件可靠性角度分析失效的深层物理成因。每一条推导后必须标注依据的知识库文档名称。
```

## 3. 各段详细规范

### 3.1 【故障现象定位】规范

#### 3.1.1 故障部件

**可选值**（必须从中选择）：

| 部件类型 | 典型日志来源 |
|---|---|
| CPU | dmesg MCE、mcelog |
| 内存 | dmesg EDAC、mcelog |
| 温度 | IPMI SEL / SDR |
| 风扇 | IPMI SEL / SDR |
| 电压 | IPMI SEL / SDR |
| 硬盘 | smartctl / dmesg |
| 电源 | IPMI SEL |
| 网卡 | ethtool / dmesg |
| PCIe | AER / dmesg |

**填写规则**：

- 能确定时：直接填写部件名称（如 CPU、内存）
- 无法确定时：输出 无法自动识别

#### 3.1.2 物理位置

**填写要求**：

- 必须具体到可操作的物理位置，便于运维人员现场定位
- 格式示例：
  - CPU：CPU 0 Bank 4、CPU 1 Socket 2
  - 内存：Channel 2, DIMM 3、DIMM_A1
  - 电源：PSU 1、PSU 2
  - 风扇：Fan 3、FAN_SYS_2
  - 硬盘：/dev/sda、Disk Slot 4
  - PCIe：Slot 3 Bus 0x04

**禁止**：

- 不能只写"CPU"或"内存"而不给具体编号
- 不能写模糊位置如"主板"

**无法提取位置时**：输出 无法定位

#### 3.1.3 报错代码

**优先级**：

1. 标准十六进制错误码（如 0x0005、0x0001）
2. IPMI 事件类型（如 nc=Non-Critical、cr=Critical、nr=Non-Recoverable）
3. 日志原文关键词（如 Internal parity error、ECC uncorrectable）

#### 3.1.4 故障等级

**可选值**（必须从中选择）：

| 故障等级 | 判定规则 |
|---|---|
| CE | 可纠正错误（Correctable Error），如 ECC CE |
| UE | 不可纠正错误（Uncorrectable Error），如 ECC UE |
| 预警 | IPMI nc（Non-Critical）事件 |
| 警告 | 需要关注但尚未达到严重级别 |
| 严重 | IPMI cr/nr（Critical/Non-Recoverable）事件、ECC UE |

**映射关系**：

- CE → 预警
- UE → 严重
- IPMI nc → 预警
- IPMI cr/nr → 严重

### 3.2 【物理根因推导】规范

#### 3.2.1 分析角度

**必须从微电子与硬件可靠性角度分析**，不能停留在"硬件坏了"的表面描述。

**可引用的物理成因**（包括但不限于）：

| 物理成因 | 英文术语 | 适用场景 |
|---|---|---|
| 单粒子翻转 | Single Event Upset (SEU) | 宇宙射线导致的比特翻转 |
| 电迁移 | Electromigration | 高电流密度下金属互连原子迁移 |
| 热疲劳 | Thermal Fatigue | 温度循环导致的焊点/封装开裂 |
| 介质击穿 | Dielectric Breakdown | 栅极氧化层退化导致漏电 |
| 金手指氧化 | Contact Oxidation | 内存/PCIe金手指接触不良 |
| Row Hammer 效应 | Row Hammer | DRAM 相邻行频繁访问导致数据翻转 |
| 电容老化 | Capacitor Aging | 电解电容容值下降导致供电不稳 |
| 信号完整性退化 | Signal Integrity Degradation | PCB 走线阻抗变化导致时序偏差 |
| NAND 磨损 | NAND Wear-out | SSD 擦写次数超限导致坏块 |
| 热载流子注入 | Hot Carrier Injection | 高能载流子注入栅极导致阈值漂移 |
| 负偏置温度不稳定性 | NBTI | PMOS 器件阈值电压漂移 |

#### 3.2.2 证据标注要求

**每一条推论后面必须标注依据的知识库文档名称**，格式为：

[依据：文档名.md]

**知识库文档列表**（可引用的依据）：

| 文档名 | 适用故障类型 |
|---|---|
| Intel_MCE错误码对照表.md | CPU MCE 错误 |
| DRAM_failure_mechanisms.md | 内存 ECC 错误 |
| memory_troubleshooting_guide.md | 内存故障排查 |
| 温度_风扇_电压告警处理规范.md | IPMI 传感器告警 |
| 电源故障判定与处置规范.md | 电源模块故障 |
| 硬盘SMART指标解读与故障判定.md | 硬盘 SMART 告警 |
| PCIe错误类型与排障指南.md | PCIe AER 错误 |
| 网卡故障诊断与处置规范.md | 网卡链路/光衰故障 |

**示例**：

判断为电迁移（Electromigration）导致的导线电阻增大。[依据：Intel_MCE错误码对照表.md]

#### 3.2.3 表述规范

| 结论类型 | 开头格式 | 示例 |
|---|---|---|
| 确定结论 | 判断为... | "判断为 CPU 内部缓存奇偶校验错误" |
| 推测性结论 | 可能为...，建议进一步确认 | "可能为 Row Hammer 效应，建议进一步确认" |
| 知识库未覆盖 | 必须输出 | 无法定位，需人工硬件检测 |

**禁止**：

- 禁止编造知识库中不存在的错误码说明
- 禁止在知识库未覆盖时自行推测根因
- 禁止使用"可能是XX坏了"等模糊表述

### 3.3 【工程处置建议】规范

必须包含三个子项，缺一不可：

#### 3.3.1 紧急处置

**要求**：值班员现场可立即执行的操作，必须具体可执行。

**示例**：

- "立即将该服务器从业务集群中摘除，切换至备机"

- "重新插拔内存条 DIMM_A1，观察是否恢复"

#### 3.3.2 根治方案

**要求**：备件调拨与硬件更换指引，必须指定：

- 具体的硬件类型和规格
- 物理位置（机房、机柜、插槽）
- 更换步骤

**示例**：

- "携带 32GB DDR4 ECC 内存条前往 A 栋 3 楼机柜 R12，更换 Channel 2, DIMM 3 插槽上的内存条"

- "调拨同型号 PSU 电源模块，更换 PSU 1"

#### 3.3.3 验证方法

**要求**：硬件更换后上电的确认和消警步骤，必须可执行、可验证。

**示例**：

- "更换后运行 memtest86+ 至少 4 小时，确认无新增 ECC 错误"
- "上电后通过 ipmitool sdr 确认所有传感器状态为 ok"
- "运行 stress-ng --cpu 0 --timeout 4h 进行 CPU 压力测试，确认无新增 MCE 错误"
- "执行 smartctl -a /dev/sda 确认 SMART 指标恢复正常"

### 3.4 【置信度评估】规范

#### 3.4.1 诊断置信度

**可选值**（必须从中选择）：

| 置信度 | 判定标准 | 典型场景 |
|---|---|---|
| 高 | 知识库完全覆盖 + 字段提取完整 | 知识库中有该错误码的完整说明，日志提供了充分的位置和错误类型信息 |
| 中 | 知识库部分覆盖 或 字段提取有缺失 | 知识库中有相关说明但不够精确，或日志信息不完整 |
| 低 | 知识库无匹配 或 日志不可解析 | 知识库未覆盖该错误码，或日志信息严重不足 |

#### 3.4.2 说明

**必须明确指出**：

1. 知识库覆盖程度（是否找到匹配的错误码/故障类型）
2. 字段提取完整性（是否成功提取位置、错误码等关键信息）
3. 如有趋势数据，说明是否参考了历史诊断记录

**示例**：

- "知识库中有该错误码的完整说明，日志提供了明确的 CPU 编号和 Bank 位置，诊断结果可信"
- "知识库中有内存 ECC 相关说明，但日志未提供具体 DIMM 编号，置信度中等"
- "知识库未覆盖此错误码，系统已自动触发兜底保护，建议人工复核"

## 7. 日志字段映射

AI 利用系统提取的结构化特征 JSON（features）填充报告模板。以下是各字段与报告段落的对应关系：

| features 字段 | 对应报告段落 | 用法说明 |
|---|---|---|
| fault_type | 故障现象定位 | 辅助判断故障大类（MCE/ECC/IPMI/SMART等） |
| component | 故障现象定位 → 故障部件 | 直接填充 |
| location | 故障现象定位 → 物理位置 | 直接填充，前端红色加粗放大显示 |
| error_code | 故障现象定位 → 报错代码 | 直接填充 |
| error_description | 物理根因推导 | 作为根因分析的起点，结合知识库展开推导 |
| severity | 故障现象定位 → 故障等级 | 直接填充，按映射规则转换 |
| vendor | 物理根因推导 / 工程处置建议 | 辅助判断是否需要厂商特定的处置建议（如 Dell/HPE/华为） |
| parse_level | 置信度评估 | vendor_specific → 置信度可偏高；generic_fallback → 中等；unknown_raw → 置信度偏低 |
| parse_warning | 置信度评估 | 若存在解析异常，置信度降级 |
| raw_key_lines | 物理根因推导 | 提供原始日志关键行供 AI 参考，辅助补充细节 |
